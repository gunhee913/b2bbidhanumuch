# 한우 부분육 B2B 경매 플랫폼 요구사항 정의서

> 작성일: 2026-06-29
> 대상 시스템: `b2bbidhanumuch` (한우 부분육 B2B 경매 플랫폼)
> 문서 버전: v1.0

---

## 1. 문서 개요

### 1.1 목적

본 문서는 현재 구현된 한우 부분육 B2B 경매 플랫폼의 기능·비기능 요구사항을 정의한다. 신규 개발 인력의 시스템 이해, 향후 기능 확장 시 기준 명세, 운영팀 인수인계, 외부 협력사 협업의 기준 문서로 활용한다.

### 1.2 범위

- 본 시스템은 **한우 부분육(20개 부위)** 을 **회차(round) 기반 경매** 방식으로 거래하는 B2B 플랫폼이다.
- 상장업체(공급자)와 중도매인(수요자) 간 거래를 중개하며, 정산·배송·알림까지 일관 처리한다.
- 일반 소비자(C-side)는 본 시스템의 대상이 아니다.
- 본 문서는 현재 구현된 기능을 기준으로 하며, 미구현·더미데이터 영역은 "7장 제약사항 및 향후 개선점"에 명시한다.

### 1.3 용어 정의

| 용어 | 정의 |
|------|------|
| 중도매인(中都買人, Dealer) | 본 플랫폼에서 한우 부분육을 입찰·낙찰받아 거래처에 공급하는 도매업체 |
| 직원(Employee) | 중도매인 또는 상장업체 소속 구성원. 대리 입찰 등을 수행 |
| 상장업체(Company) | 한우를 도축·가공하여 부분육을 본 플랫폼에 상장(등록)하는 공급자(출하주) |
| 관리자(Admin) | 플랫폼 운영 주체. `master`와 일반 `admin`으로 구분 |
| 상장(Listing) | 경매 대상으로 등록된 한 마리 개체(소)의 부분육 정보 |
| 개체 | 도축된 한 마리 단위. 상장 1건 = 개체 1마리 = 부분육 20부위 |
| 부분육(Part) | 개체를 20개 부위로 분할한 단위. 입찰의 기본 단위 |
| 경매(Auction) | 본 시스템에서는 1개 회차를 의미하는 단위 |
| 회차(Round) | 같은 날의 경매를 시간 단위로 분할한 진행 단위 (1회차, 2회차…) |
| 세션(Session) | 같은 날의 모든 회차를 묶는 단위. `session_id`로 식별 |
| 사전 배정 모드 | 회차별로 상장을 사전 분배한 뒤 순차적으로 진행하는 경매 방식 |
| 재경매 모드 | 미낙찰 상장을 다시 모아 즉시 새로운 회차를 여는 방식 |
| 거래처(Partner) | 중도매인이 낙찰 부위를 최종 납품하는 음식점·정육점·마트 등 |
| 낙찰 | 부위별 최고가 입찰을 확정하는 행위 (`is_winning = true`) |
| 유찰 | 최저가에 미달하거나 입찰이 없어 낙찰되지 않은 상태 |
| FCM | Firebase Cloud Messaging. 모바일 푸시 알림 채널 |

## 2. 시스템 개요

### 2.1 시스템 정의

한우 부분육을 **회차 기반 비공개 입찰(closed-bid)** 방식으로 거래하는 B2B 플랫폼이다. 상장업체가 등록한 개체별 20부위에 대해 중도매인이 단가(원/kg)로 입찰하며, 회차 마감 시점에 부위별 최고가 입찰자가 낙찰자로 자동 확정된다.

### 2.2 기술 스택

- **프론트엔드**: Next.js 15 (App Router, Turbopack), React 19, TypeScript, Tailwind CSS, shadcn-ui
- **상태관리**: TanStack Query(서버 상태), Zustand(전역 상태)
- **백엔드**: Next.js API Routes (Node.js 런타임)
- **데이터베이스**: Supabase (PostgreSQL + RLS + Realtime)
- **인증**: NextAuth v4 (JWT 전략) + 모바일용 자체 JWT(`jose`)
- **푸시 알림**: Firebase Cloud Messaging (FCM)
- **호스팅**: Vercel

### 2.3 시스템 영역 구조

플랫폼은 사용자 유형에 따라 4개 영역으로 구분된다.

- **중도매인 모바일 영역** (루트 경로 `/`): 모바일 최적화된 입찰·경매 참여 UI
- **중도매인 데스크톱 영역** (`/dealer`): 데스크톱용 통계·조회·엑셀 다운로드
- **상장업체 영역** (`/company`): 상장 등록·경매 모니터링·정산·출고
- **관리자 영역** (`/admin`): 회원·경매·정산·배송·콘텐츠 전반 운영

각 영역은 별도의 로그인 페이지와 사용자 유형을 가지며, 단일 브라우저에서는 한 번에 하나의 영역에만 로그인할 수 있다.

## 3. 사용자 역할 정의

### 3.1 사용자 유형

본 시스템에는 3가지 최상위 사용자 유형이 존재한다.

#### 3.1.1 중도매인 (`dealer_user`)

- 한우 부분육 경매에 입찰하는 도매업체 및 그 소속 직원
- 하위 역할: `dealer`(대표 계정), `employee`(소속 직원)
- 권한:
  - 모바일·데스크톱 영역 전체 이용
  - 부위별 입찰·재입찰·관심 등록
  - 본인 낙찰 내역·정산·잔고 조회
  - 낙찰 부위에 대한 거래처 배정
  - 본인 알림·공지 조회
- 로그인 ID: 전화번호 (중도매인 본인 또는 직원의 phone)

#### 3.1.2 상장업체 직원 (`company_user`)

- 한우 부분육을 상장하는 업체의 직원
- 하위 역할: `대표`, `직원` 등 자유 텍스트
- 권한:
  - 자사 명의 상장 등록·수정·삭제 (마감 전까지)
  - 자사 상장의 경매 진행 상황 실시간 모니터링
  - 자사 매출·정산서·출고지시서 조회
- 로그인 ID: 직원의 전화번호 (업체 자체는 로그인 불가)
- 제약: 소속 업체가 `active` 상태일 때만 로그인 가능

#### 3.1.3 관리자 (`admin_user`)

- 플랫폼 전체 운영 권한 보유
- 하위 역할: `master`(마스터권한), `admin`(일반 관리자)
- 권한:
  - 회원(중도매인/상장업체/관리자) 등록·수정·삭제
  - 상장 승인·반려
  - 경매 회차 생성·시작·마감·취소
  - 정산 수수료 설정 및 입출금 처리
  - 거래처(파트너) 관리
  - 공지·약관·사이트 콘텐츠 관리
  - 알림 템플릿·수동 발송
- 로그인 시 IP 주소 기록 (`last_login_ip`)

### 3.2 계정 상태

- 모든 사용자 계정은 `active` / `inactive` 상태를 가진다.
- `inactive` 계정은 로그인 자체가 거부된다.
- 비밀번호는 모두 bcrypt로 해시되어 저장된다.

### 3.3 인증 채널

- **웹**: NextAuth JWT 쿠키 세션 (만료 24시간)
- **모바일 앱**: Bearer JWT (access 24시간 + refresh 30일). 단, 중도매인 유형만 지원
- 두 채널 모두 동일한 DB의 사용자 정보를 검증한다.

## 4. 기능 요구사항

### 4.1 회원·인증 (FR-AUTH)

- **FR-AUTH-01** 시스템은 중도매인/상장업체/관리자 3가지 유형에 대해 각각 분리된 로그인 페이지(`/login`, `/company/login`, `/admin/login`)를 제공해야 한다.
- **FR-AUTH-02** 모든 로그인은 전화번호와 비밀번호를 입력받아 bcrypt 해시로 검증한다.
- **FR-AUTH-03** 중도매인 로그인 시 시스템은 `dealers` 테이블에서 먼저 검색하고, 미일치 시 `dealer_employees`에서 검색한다.
- **FR-AUTH-04** 로그인 성공 시 시스템은 사용자 유형에 따른 세션을 발급하고, 마지막 로그인 시각(`last_login_at`)을 갱신한다.
- **FR-AUTH-05** 관리자 로그인 시 시스템은 클라이언트 IP를 추출하여 `last_login_ip`에 저장한다.
- **FR-AUTH-06** 시스템은 중도매인용 별도 **경매 비밀번호**를 제공한다. 입찰 시 클라이언트 설정(`auctionPasswordEnabled`)이 활성화된 경우 경매 비밀번호 재인증을 요구한다.
- **FR-AUTH-07** 경매 비밀번호 인증 유효기간은 인증 당일 자정까지로 한다.
- **FR-AUTH-08** 시스템은 모바일 앱 클라이언트를 위한 별도 JWT 발급/갱신/세션 API(`/api/auth/mobile/login`, `/refresh`, `/session`)를 제공한다.
- **FR-AUTH-09** 보호된 페이지에 비로그인 상태로 접근 시 시스템은 해당 영역의 로그인 페이지로 리다이렉트하며, `callbackUrl` 파라미터로 원래 경로를 보존한다.
- **FR-AUTH-10** 한 사용자 유형으로 로그인한 상태에서 타 유형 전용 페이지 접근 시 해당 유형의 로그인 페이지로 리다이렉트된다.

### 4.2 상장 관리 (FR-LIST)

#### 4.2.1 상장 등록

- **FR-LIST-01** 상장업체 직원과 관리자는 개체(한 마리) 단위로 상장을 등록할 수 있다.
- **FR-LIST-02** 등록 시 시스템은 다음 정보를 수집한다.
  - 개체 정보: 축종(기본 한우), 성별(거세/암/수), 등급, 근내지방도(1~9), 월령
  - 이력 정보: 이력번호, 도축장, 도축일, 도축번호, 도체중
  - 등급 판정: 등박지방, 등심단면적, 육색, 지방색, 조직감, 성숙도
  - 가공 정보: 가공일, 가공중량, 도축증명서, 등급판정서
  - 부위 정보: 20개 부위별 중량(kg), 최저가(원/kg), 상장 포함 여부
  - 이미지: 다수 업로드 가능 (Supabase Storage 저장)
- **FR-LIST-03** 시스템은 등록 시 접수번호(`listing_no`)를 자동 부여한다. 형식은 `YYMMDD-{업체번호 첫자리}{순번}` (예: `260203-101`).
- **FR-LIST-04** 등록된 상장의 초기 상태는 `pending`이며, 관리자 승인을 거쳐야 `approved` 상태가 된다.
- **FR-LIST-05** 시스템은 등록 시점에 해당 상장일이 이미 `auction_close_dates`에 마감 기록된 날짜인지 확인하여, 마감된 날짜에 대한 신규 상장 등록을 차단한다.
- **FR-LIST-06** 상장업체 직원은 Excel 일괄 업로드 기능을 통해 다수의 개체를 한 번에 등록할 수 있다.

#### 4.2.2 상장 상태 전이

- **FR-LIST-07** 상장의 상태는 다음 순서로 전이된다.
  - `pending` → `approved` → `auction` → `closed`/`completed`
  - 등록 직후 미승인 상태는 `cancelled`로 폐기 가능
- **FR-LIST-08** `pending` 상태의 상장만 삭제할 수 있다.
- **FR-LIST-09** 관리자는 `closed` 상태의 상장을 `reopen`하여 `approved`로 되돌릴 수 있으나, 이후 날짜가 마감 기록되어 있으면 reopen은 거부된다.

#### 4.2.3 부위 관리

- **FR-LIST-10** 모든 개체는 20개 부위로 구성된다. (등심, 안심, 채끝, 양지, 우둔, 설도, 사태, 갈비, 치마, 부채, 업진, 토시, 제비 등; DB 정의 기준)
- **FR-LIST-11** 부위별로 최저가(`min_price`, 원/kg) 설정이 가능하다.
- **FR-LIST-12** 상장 포함 여부(`is_included`)를 부위 단위로 토글할 수 있어, 일부 부위만 경매에 올릴 수 있다.

### 4.3 경매·회차 운영 (FR-AUCTION)

#### 4.3.1 경매 구조

- **FR-AUCTION-01** 경매는 일자별 세션(`session_id`)으로 묶이며, 세션은 여러 개의 회차(round)로 구성된다.
- **FR-AUCTION-02** 1회차의 ID가 해당 세션의 `session_id`로 사용된다.
- **FR-AUCTION-03** 각 회차는 다음 시간 속성을 가진다.
  - 회차 진행 시간 (`round_duration_min`, 기본 5분)
  - 회차 간 텀 (`term_duration_min`, 기본 2분)
  - 자동 다음 회차 진행 여부 (`auto_next_round`, 기본 true)
  - 재경매 시간 (`reauction_duration_min`)

#### 4.3.2 경매 운영 모드

- **FR-AUCTION-04** 시스템은 두 가지 경매 운영 모드를 지원한다.
  - **사전 배정 모드**: 관리자가 회차별로 상장을 미리 분배 후 1회차부터 순차 진행
  - **재경매 모드**: 해당일 승인된 상장 전체를 새 회차에 모아 즉시 시작
- **FR-AUCTION-05** 사전 배정 모드 사용 시 관리자는 드래그앤드롭 UI로 회차별 상장을 편집·저장할 수 있다.
- **FR-AUCTION-06** 재경매 시작 시 이미 `open` 상태의 회차가 존재하면 409 오류로 거부된다.

#### 4.3.3 회차 생명주기

- **FR-AUCTION-07** 회차 상태는 `scheduled` → `open` → `closed` 또는 `cancelled` 로 전이된다.
- **FR-AUCTION-08** 관리자는 `open` 상태의 회차를 즉시 시작(`/start-now`)하여 텀을 건너뛸 수 있다.
- **FR-AUCTION-09** 회차 마감(`close_round` RPC) 시 시스템은 다음을 수행한다.
  - 해당 회차에 연결된 상장의 부위별 입찰을 가격 내림차순, 시각 빠른 순으로 정렬
  - 1위 입찰에 `is_winning = true`, `rank = 1` 설정
  - 회차 상태를 `closed`로 변경
  - 자동 진행이 활성화되어 있으면 텀 후 다음 회차를 `open`으로 전환
  - 입찰자별로 낙찰/유찰 결과 알림(`auction_result`) 발송
- **FR-AUCTION-10** 관리자는 `open` 상태의 재경매를 취소할 수 있으며, 취소 시 해당 회차에 연결된 상장은 `closed`(유찰)로 처리된다.
- **FR-AUCTION-11** 관리자는 해당일의 모든 경매를 초기화할 수 있다. 초기화 시 입찰·낙찰 정보가 삭제되고 상장은 `approved`로 복원된다.

#### 4.3.4 실시간 경매 모니터링

- **FR-AUCTION-12** 진행 중인 회차에 대해 시스템은 Supabase Realtime 기반으로 실시간 입찰·낙찰가 변동을 클라이언트에 푸시한다.
- **FR-AUCTION-13** 상장업체 직원은 자사 상장에 대한 실시간 경매 현황(`/company/auctions/live`)을 모니터링할 수 있다.
- **FR-AUCTION-14** 관리자는 전체 경매의 실시간 입찰 내역을 모니터링하며 수동 시작·마감 제어가 가능하다.

### 4.4 입찰 (FR-BID)

#### 4.4.1 입찰 규칙

- **FR-BID-01** 입찰의 단위는 **부위(part)** 이며, 입찰가는 단가(원/kg)로 입력한다.
- **FR-BID-02** 입찰금액은 시스템이 자동 계산한다: `bid_amount = round(bid_price × weight)`.
- **FR-BID-03** 한 중도매인은 동일 부위에 대해 1건의 입찰만 보유한다. 재입찰 시 기존 입찰이 UPDATE된다. (DB 제약: `UNIQUE(part_id, dealer_id)`)
- **FR-BID-04** 입찰가는 해당 부위의 `min_price` 이상이어야 한다.
- **FR-BID-05** 입찰 가능한 상장은 `approved` 또는 `auction` 상태이며, 동시에 현재 `open` 상태의 회차에 배정되어 있어야 한다.
- **FR-BID-06** 입찰 시점이 회차의 `started_at + round_duration_min`을 초과한 경우 입찰은 거부된다.
- **FR-BID-07** 시스템은 입찰 요청 시 사용자 인증(`resolveAuth`)을 우선 검증하며, 실패 시 클라이언트가 전달한 `dealerId`로 fallback할 수 있다. (보안 강화 필요 사항으로 7장에 명시)

#### 4.4.2 낙찰 결정

- **FR-BID-08** 부위별 낙찰자는 `bid_price` 내림차순, 동률 시 `created_at` 빠른 순으로 결정된다.
- **FR-BID-09** 회차 마감 시 부위별 1위 입찰에 `is_winning = true`, `rank = 1`이 설정되며, `cattle_parts.winning_dealer_id`, `bid_price`, `bid_amount`, `bid_at`이 자동 갱신된다. (DB 트리거 `trigger_update_part_on_winning`)
- **FR-BID-10** 시스템은 모든 입찰 수정·삭제 이력을 `bid_audit_logs`에 기록한다.

#### 4.4.3 관심 등록

- **FR-BID-11** 중도매인은 상장 또는 부위 단위로 관심(즐겨찾기)을 등록할 수 있다.
- **FR-BID-12** 관심 등록은 중도매인 계정 단위로 공유되며, 일자(`active_date`)별로 별도 관리된다.

### 4.5 정산 (FR-SETTLE)

#### 4.5.1 정산 수수료 설정

- **FR-SETTLE-01** 관리자는 정산 수수료 항목을 추가·삭제·수정할 수 있다.
- **FR-SETTLE-02** 각 수수료 항목은 다음 속성을 갖는다.
  - 이름 (예: 상장수수료, 물류비, 상차비)
  - 유형: `percentage`(비율) 또는 `fixed`(고정 금액)
  - 값, 활성화 여부, 정렬 순서
- **FR-SETTLE-03** 초기 시드 데이터로 상장수수료 1.5%, 물류비 21,000원, 상차비 20,000원이 설정되어 있다.

#### 4.5.2 상장업체 정산

- **FR-SETTLE-04** 시스템은 마감된 상장의 낙찰 금액에서 수수료를 차감하여 상장업체별 실지급액을 산출한다.
- **FR-SETTLE-05** 상장업체와 관리자는 기간별 정산서를 조회·인쇄·Excel 다운로드할 수 있다.
- **FR-SETTLE-06** 정산서에는 개체별 매출, 부위별 낙찰가, 수수료 항목별 차감액, 실수령액이 표시된다.

#### 4.5.3 중도매인 정산 및 잔고

- **FR-SETTLE-07** 중도매인 정산은 낙찰 금액 전액 지급 기준이며, 별도 수수료가 차감되지 않는다.
- **FR-SETTLE-08** 시스템은 중도매인별 가용잔액을 다음 공식으로 산출한다.
  - `가용잔액 = 총입금 - 총출금 - 미정산 낙찰대금(is_winning bids 합계)`
- **FR-SETTLE-09** 관리자는 중도매인 단위로 입금·출금 거래를 등록·수정·취소할 수 있다.
- **FR-SETTLE-10** 거래 등록·수정·취소 시 관리자 비밀번호(`ADMIN_BID_PASSWORD` 환경변수) 검증을 요구한다.
- **FR-SETTLE-11** 모든 입출금 거래 수정 이력은 `dealer_transaction_edits`에 기록된다.
- **FR-SETTLE-12** 중도매인은 본인의 잔고 내역을 일자·유형 필터와 함께 조회할 수 있다.

### 4.6 배송·거래처 (FR-DEL)

#### 4.6.1 거래처 관리

- **FR-DEL-01** 관리자는 거래처(파트너) 마스터를 등록·수정·삭제할 수 있다.
- **FR-DEL-02** 거래처 번호(`partner_no`)는 등록 시 자동으로 `10001`부터 순차 부여된다. (DB 트리거 `trigger_generate_partner_no`)
- **FR-DEL-03** 각 거래처는 담당 중도매인을 최대 3명(`dealer1_id`~`dealer3_id`)까지 연결할 수 있다.
- **FR-DEL-04** 거래처는 업종(음식점, 정육점, 마트 등) 속성을 가진다.

#### 4.6.2 거래처 배정

- **FR-DEL-05** 중도매인은 본인이 낙찰받은 부위에 대해 최종 납품할 거래처를 지정할 수 있다.
- **FR-DEL-06** 한 부위는 한 거래처에만 배정 가능하다. (DB 제약: `UNIQUE(part_id)`)
- **FR-DEL-07** 배정 정보는 Supabase Realtime으로 클라이언트 간 동기화된다.

#### 4.6.3 출고지시서

- **FR-DEL-08** 상장업체 직원은 자사 상장의 낙찰 부위에 대한 출고지시서를 조회·인쇄할 수 있다.
- **FR-DEL-09** 출고지시서에는 거래처 정보, 부위 정보, 중량, 낙찰 중도매인 정보가 포함된다.
- **FR-DEL-10** 관리자는 전체 출고 현황을 조회하며 라벨 인쇄 등 부가 기능을 사용할 수 있다.

### 4.7 알림·공지 (FR-NOTI)

#### 4.7.1 알림 유형

- **FR-NOTI-01** 시스템은 다음 4종의 알림 유형을 지원한다.
  - `listing_upload`: 상장 등록 안내
  - `auction_start`: 경매 시작 안내
  - `auction_result`: 입찰 결과 (낙찰/유찰)
  - `balance`: 잔고 변동 (입금/출금)

#### 4.7.2 알림 발송

- **FR-NOTI-02** 시스템은 비즈니스 이벤트 발생 시 자동으로 DB에 알림 레코드를 생성하고 FCM 푸시를 발송한다.
- **FR-NOTI-03** 관리자는 알림 유형별로 전역 활성화/비활성화를 설정할 수 있다.
- **FR-NOTI-04** 중도매인은 본인의 알림 유형별 수신 여부를 개별 설정할 수 있다. (전역 활성화 + 개인 활성화 모두 true일 때 발송)
- **FR-NOTI-05** 관리자는 알림 제목·메시지 템플릿을 변수 치환(`{변수명}`) 형태로 편집할 수 있다.
- **FR-NOTI-06** 관리자는 수동으로 전체 또는 특정 중도매인에게 알림을 발송할 수 있으며, 모든 발송은 `notification_logs`에 기록된다.
- **FR-NOTI-07** 시스템은 등급별 상장 두수 테이블을 자동 생성하여 상장 업로드 알림에 포함할 수 있다.

#### 4.7.3 디바이스 토큰

- **FR-NOTI-08** 모바일 앱은 FCM 디바이스 토큰을 `device_tokens` 테이블에 등록한다.
- **FR-NOTI-09** 각 토큰은 플랫폼(`android` 또는 `ios`) 정보와 함께 저장된다.

#### 4.7.4 공지사항

- **FR-NOTI-10** 관리자는 공지사항을 CRUD할 수 있으며, HTML 본문 편집을 지원한다.
- **FR-NOTI-11** 공지사항은 카테고리(일반/경매일정/휴무/시스템), 대상(`all`/`dealer`/`company`), 고정 여부, 게시 여부 속성을 가진다.
- **FR-NOTI-12** 관리자는 경매 일정 캘린더 HTML을 자동 생성하여 공지에 첨부할 수 있다.

#### 4.7.5 사이트 콘텐츠

- **FR-NOTI-13** 관리자는 이용약관(`terms`), 개인정보처리방침(`privacy`)을 편집할 수 있다.
- **FR-NOTI-14** 관리자는 푸터에 노출되는 사업장 정보(상호, 대표자, 주소, 사업자등록번호, 통신판매업 신고번호, 영업시간 등)를 편집할 수 있다.

### 4.8 통계·리포트 (FR-RPT)

- **FR-RPT-01** 시스템은 사용자 유형별 대시보드를 제공한다.
  - 중도매인 대시보드: 본인 입찰·낙찰 통계, 일별·부위별·거래처별 집계
  - 상장업체 대시보드: 자사 경매 두수·낙찰·수수료, 부위/등급/중도매인별 집계
  - 관리자 대시보드: 전체 경매·낙찰·수수료, 업체/부위/등급/중도매인별 집계
- **FR-RPT-02** 시스템은 부위·등급별 시세 조회를 제공하며, 일·주·월 평균을 차트(lightweight-charts)로 시각화한다.
- **FR-RPT-03** 시스템은 부위별 낙찰률(상장 대비 낙찰 비율) 통계를 기간 필터와 함께 제공한다.
- **FR-RPT-04** 모든 통계 화면은 Excel 다운로드 기능을 제공한다.
- **FR-RPT-05** 관리자는 상장업체 및 중도매인 단위 순위 리포트를 조회할 수 있다. (현재 일부 더미 데이터 기반, 7장 참조)

## 6. 비기능 요구사항

### 6.1 실시간성

- **NFR-RT-01** 경매·입찰·낙찰가 변동·배송 배정은 Supabase Realtime publication을 통해 서버 푸시 방식으로 클라이언트에 반영되어야 한다. (대상 테이블: `auctions`, `bids`, `delivery_assignments`)
- **NFR-RT-02** 실시간 화면(`/`, `/admin/auctions/live`, `/company/auctions/live`)에서 입찰 등록·낙찰 변동은 폴링 없이 즉시 반영되어야 한다.
- **NFR-RT-03** 회차 타이머는 클라이언트에서 정확한 카운트다운을 표시하며, 회차 마감 시각(`started_at + round_duration_min`) 도래 시 자동으로 입찰을 차단해야 한다.

### 6.2 보안

- **NFR-SEC-01** 모든 비밀번호(로그인·경매)는 bcrypt로 해시되어 저장되며, 평문은 어떠한 경우에도 저장·로깅되지 않아야 한다.
- **NFR-SEC-02** Supabase 접근은 일반 클라이언트(`anon`)와 관리용 클라이언트(`service_role`)를 분리하며, `service_role` 키는 서버 환경변수로만 노출되어야 한다.
- **NFR-SEC-03** 관리자 전용 API는 NextAuth JWT에서 `userType === 'admin_user'`를 검증한 후에만 동작해야 한다.
- **NFR-SEC-04** 중도매인 전용 API는 Bearer JWT 또는 NextAuth 쿠키에서 `dealerId`를 추출하여 본인 데이터에만 접근하도록 제한해야 한다.
- **NFR-SEC-05** 보호된 페이지 라우트는 `src/middleware.ts`를 통해 사용자 유형별 접근 제어가 이루어져야 한다.
- **NFR-SEC-06** 입찰 수정·삭제, 입출금 등록 등 민감 작업은 관리자 비밀번호를 추가 인증으로 요구해야 한다.
- **NFR-SEC-07** 모든 입찰 수정·삭제 이력은 감사 로그(`bid_audit_logs`)에 보관되어야 한다.

### 6.3 성능

- **NFR-PERF-01** 페이지 초기 로딩은 모바일 4G 환경에서 3초 이내를 목표로 한다.
- **NFR-PERF-02** 입찰 등록 API는 정상 응답을 500ms 이내에 반환해야 한다.
- **NFR-PERF-03** 대시보드·통계 화면은 기간 필터 변경 시 2초 이내에 갱신되어야 한다.
- **NFR-PERF-04** 회차 마감(`close_round` RPC)은 상장 100건 이내 규모에서 5초 이내에 완료되어야 한다.
- **NFR-PERF-05** 서버 상태 캐싱은 TanStack Query를 통해 일관되게 관리되어야 한다.

### 6.4 호환성

- **NFR-COMP-01** 모바일 영역은 iOS Safari, Android Chrome 최신 2개 버전을 지원해야 한다.
- **NFR-COMP-02** 데스크톱 영역은 Chrome, Edge, Safari 최신 2개 버전을 지원해야 한다.
- **NFR-COMP-03** 데스크톱 페이지는 1280px 이상의 뷰포트를 기준으로 한다.
- **NFR-COMP-04** 모바일 페이지는 360px 이상의 뷰포트에서 정상 동작해야 한다.

### 6.5 데이터 무결성

- **NFR-DATA-01** 부위별 입찰은 `UNIQUE(part_id, dealer_id)` 제약으로 중도매인당 1건만 허용되어야 한다.
- **NFR-DATA-02** 거래처 배정은 `UNIQUE(part_id)` 제약으로 부위당 1건만 허용되어야 한다.
- **NFR-DATA-03** 접수번호(`listing_no`), 경매번호(`auction_no`), 거래처번호(`partner_no`)는 시스템이 자동 부여하며 중복되지 않아야 한다.
- **NFR-DATA-04** 낙찰 정보 갱신은 DB 트리거(`trigger_update_part_on_winning`)를 통해 일관성을 보장해야 한다.
- **NFR-DATA-05** 마감된 날짜에 대한 신규 상장 등록은 시스템 차원에서 차단되어야 한다.

### 6.6 운영·배포

- **NFR-OPS-01** 시스템은 Vercel을 통한 자동 배포를 사용하며, `main` 브랜치 푸시가 곧 운영 배포로 연결된다.
- **NFR-OPS-02** Supabase 마이그레이션은 `/supabase/migrations/` 디렉터리에 SQL 파일로 보관·관리되어야 한다.
- **NFR-OPS-03** 환경변수는 `.env.local`(로컬), Vercel 환경변수(운영)로 분리 관리되며 저장소에 커밋되지 않아야 한다.

## 7. 제약사항 및 향후 개선점

본 시스템에서 발견된 미구현 영역, 일관성 부족 지점, 보안 강화가 필요한 부분을 정리한다.

### 7.1 미구현·더미 데이터 영역

- **C-01** `/admin/users` 통합 회원 목록 화면은 더미 데이터를 사용 중이다. 실 API 연동 필요.
- **C-02** `/admin/reports/company-ranking`, `/admin/reports/dealer-ranking` 리포트는 더미 데이터 기반이다. `bids`/`settlements` 데이터를 기반으로 한 실 통계 API 필요.
- **C-03** `/admin/market` 시세 조회 일부 항목이 더미 데이터를 포함하고 있다.

### 7.2 권한·인증 일관성

- **C-04** `master`와 `admin` 역할은 DB·UI에만 존재하며, API 권한 분기 코드가 구현되어 있지 않다. 마스터 전용 기능(예: 관리자 계정 관리) 정의 및 권한 분리 필요.
- **C-05** `/dealer/*` 경로는 NextAuth middleware의 보호 목록에 포함되어 있지 않다. 보호 추가 권장.
- **C-06** `/api/admin/*` 일부 CRUD 라우트는 서버 측 인증 검증이 없고, 페이지 미들웨어 보호에만 의존한다. API 직접 호출 시 우회 가능하므로 라우트별 `getToken()` 검증 일관 적용 필요.
- **C-07** 입찰 API의 fallback 로직(`resolveAuth` 실패 시 클라이언트 `dealerId` 사용)은 보안 검토 후 제거 또는 강화 필요.

### 7.3 운영 보안

- **C-08** `ADMIN_BID_PASSWORD` 환경변수의 기본값이 `1234`로 설정되어 있어, 운영 환경에서는 반드시 강력한 값으로 교체되어야 한다.
- **C-09** Service role 키 노출 방지를 위해 클라이언트 코드에서 해당 키가 import되지 않는지 정기 점검 필요.
- **C-10** Vercel 배포 시 보안 의존성(React/Next.js 등) CVE 대응을 위한 정기 업그레이드 정책 수립 필요.

### 7.4 데이터·로직 단순화

- **C-11** `bids.auction_id`가 nullable로 단순화되어 있어, 회차와 입찰 간 연결이 약하다. 분석 쿼리 작성 시 `cattle_parts.listing_id → auction_listings`를 경유해야 함에 유의.
- **C-12** `close_listing`(레거시), `close_auction`(레거시), `close_round`(현행) 3종 DB 함수가 공존한다. 운영 안정화 후 레거시 함수 정리 권장.
- **C-13** 모바일 JWT 인증은 중도매인 유형만 지원한다. 향후 상장업체·관리자용 모바일 앱 확장 시 인증 확장 필요.

### 7.5 UX·중복 화면

- **C-14** 경매장 메인 `/`와 대체 뷰 `/auction`이 기능적으로 유사하다. 통합 또는 역할 명확화 검토 필요.
- **C-15** 로그인 페이지 `/login`과 `/dealer/login`이 동일한 Provider를 사용한다. 리다이렉트 목적지만 다르므로 단일 페이지화 검토 가능.
